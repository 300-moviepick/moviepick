# 리뷰 좋아요순 목록 11초 → 결과 캐시로 11ms

> 좋아요 수를 매번 집계하는 정렬 쿼리를 앞 5페이지 결과 캐시로 감싸, p95 11,078ms를 11.13ms로 줄였습니다.

## 문제
전체 리뷰 좋아요순 목록(`GET /api/movies/reviews?sort=likes`)이 50명 동시 요청에서 p95 11,078ms였습니다. 통과 기준(p95 500ms)의 약 22배입니다.

## 원인
- 좋아요 수를 컬럼에 두지 않고 `review_likes`에서 세는 구조입니다. 컬럼 값과 실제 좋아요 수가 어긋나지 않게 하려고 고른 방식입니다.
- 좋아요순 정렬은 리뷰마다 좋아요를 세는 상관 하위 쿼리로 만들어집니다(`ReviewRepository`). 리뷰 10만 건 전체를 정렬한 뒤 20개만 잘랐습니다.

## 해결
- 좋아요순일 때만 `ReviewListCacheService`를 거치게 했습니다(`ReviewController`).
- `@Cacheable(sync = true)`로 앞 5페이지(page 0~4)를 Redis에 3분 동안 캐시합니다(`ReviewListCacheService`, `RedisConfig`). `sync = true`라 캐시가 빈 순간 몰린 요청도 한 번만 계산합니다.
- 같은 클래스 안에서 부르면 캐시 프록시를 거치지 않으므로 캐시 메서드를 별도 빈으로 뺐습니다.
- 응답에 회원별 값이 없는 목록이라 페이지 전체를 캐시해도 됩니다.

## 결과
| 조건 | 전 | 후 |
|---|---|---|
| 50명 동시 요청 p95 | 11,078ms | **11.13ms** |
| 500명 동시 요청 p95 (개선 후 한계 측정) | 50명에서 이미 미달 | 44ms |

k6 50명 동시 요청 p95, 로컬 측정, 같은 측정자·같은 PC 전후 비교입니다.
`ReviewListCacheServiceTest`가 같은 페이지는 한 번만 계산하고 page 5부터는 캐시하지 않는지 확인합니다.

**남은 한계**: page 5부터와 캐시가 빈 첫 요청은 여전히 느린 쿼리를 탑니다. 캐시를 지우는 코드가 없어 좋아요 순서가 최대 3분 늦게 반영됩니다.

## 배운 점
정확성을 위해 고른 집계 방식도 부하 측정으로 비용을 확인해야 합니다. 캐시는 대상 조건·페이지 범위·최신성(TTL)을 함께 정해야 합니다.
